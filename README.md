# Метод підвищення точності аналізу табличних даних у RAG-системах на основі ітеративної генерації та верифікації коду

Програмна реалізація магістерської кваліфікаційної роботи.
Автор: Слободян П. Т., група КНСШ-22, кафедра систем штучного інтелекту,
Національний університет «Львівська політехніка», 2026.

Система відповідає на запитання до табличних даних. Замість прямої відповіді
мовної моделі вона генерує код pandas, виконує його на всій таблиці та
перевіряє результат без еталонної відповіді: відповідь приймається, якщо з нею
збігається відповідь незалежного прямого маршруту (верифікація згодою
маршрутів). Якщо результат виконання коду вказує на хибно обрану таблицю,
система виконує повторний пошук таблиці.

Усі числові результати з джерелом кожного числа наведено у файлі
[RESULTS.md](RESULTS.md). У цьому файлі описано, як ці результати відтворити.

## 1. Структура репозиторію

| Папка | Призначення |
|---|---|
| `core/` | конвеєр обробки запиту, пісочниця для виконання коду, верифікація відповідей, перевірка застосовності запиту, мовні профілі |
| `generation/` | клієнт мовних моделей (Groq, Gemini, тестовий режим mock), класифікатор типу запитання |
| `ingestion/` | завантаження FinQA, TAT-DQA і DataBench, витягування таблиць із PDF, каталог таблиць і пошук BM25 |
| `retrieval/` | структурний і векторний індекси, об'єднання результатів методом RRF |
| `eval/` | скрипти експериментів, кеші прогонів, звіти та графіки |
| `demo/`, `app.py` | вебінтерфейс на Streamlit |
| `tests/` | тести |
| `data/` | розмічені набори для класифікатора типу запитання; решта даних завантажується скриптами |

Модулі запускаються як пакети з кореня проєкту: `python -m eval.X`, а не
`python eval/X.py`. Пошук таблиці виконується поза `pipeline.run()`: ця функція
приймає вже знайдені назви таблиць.

## 2. Встановлення

Потрібен Python 3.12.

```bash
python -m venv venv
./venv/Scripts/python.exe -m pip install -r requirements.txt
./venv/Scripts/python.exe -m pip install databench-eval
```

Команди наведено для bash (на Windows для Git Bash). На Linux і macOS замість
`./venv/Scripts/python.exe` використовується `./venv/bin/python`. На Windows
команди запускаються зі змінною `PYTHONUTF8=1`.

Пакет `databench-eval` організаторів SemEval-2025 Task 8 містить офіційну
функцію порівняння відповідей `Evaluator.default_compare`. Усі результати на
DataBench отримано саме нею, що забезпечує їх порівнянність з опублікованими
результатами змагання.

### Ключі API

Ключі задаються у файлі `.env` у корені проєкту (зразок у `.env.example`):

```
GROQ_API_KEY=...
GEMINI_API_KEY=...
```

Без ключів використовується тестовий провайдер `mock`. Його достатньо для
регресійних тестів, але не для прогонів експериментів.

### Змінні оточення

| Змінна | Призначення |
|---|---|
| `VKSK_LLM_PROVIDER` | провайдер моделі: `groq`, `gemini` або `mock` |
| `VKSK_LLM_MODEL` | модель: `openai/gpt-oss-120b` або `gemini-flash-lite-latest` |
| `VKSK_LANG` | мова профілю: `en` (за замовчуванням) або `uk` |
| `VKSK_TOKEN_LEDGER` | файл обліку витрачених токенів; без цієї змінної облік не ведеться, тому її слід задавати для кожного прогону |

## 3. Перевірка встановлення

Перевірка виконується на синтетичних даних (підрозділ 3.4.1 роботи) і не
потребує ключів API. Спочатку формуються тестові PDF-документи:

```bash
PYTHONUTF8=1 VKSK_LANG=uk ./venv/Scripts/python.exe -m ingestion.make_sample_pdf
```

Ці документи не зберігаються в репозиторії, оскільки повністю визначаються
таблицями з `ingestion/synthetic_data.py`. Далі запускається регресійний тест:

```bash
PYTHONUTF8=1 VKSK_LANG=uk VKSK_LLM_PROVIDER=mock \
  ./venv/Scripts/python.exe -m eval.eval
# контрольна сума eval_results.csv має дорівнювати 9dcab6cf0be8dbd56673c9b374154f3f
```

Контрольна сума обчислюється за файлом результатів `eval_results.csv`, а не за
PDF: бібліотека `reportlab` записує в документ час створення, тому PDF
відрізняються байтами, а витягнуті з них таблиці збігаються. Розбіжність
контрольної суми означає, що змінився код у `core/` або `generation/`.

Додаткові перевірки:

```bash
./venv/Scripts/python.exe -m tests.test_lang          # 60 перевірок мовних профілів
./venv/Scripts/python.exe -m eval.eval_invariants     # 12 інваріантів
```

## 4. Дані

| Набір | Спосіб отримання | Обсяг |
|---|---|---|
| FinQA | завантажується модулем `ingestion/finqa_loader.py` під час першого звернення | – |
| DataBench | таблиці завантажуються з HuggingFace скриптом `eval/databench_prep.py` | близько 60 таблиць, 3.2 млн рядків |
| TAT-DQA | архів `tatdqa_docs_dev.zip` розпаковується вручну в `data/tatdqa/` | близько 157 МБ |

```bash
# вибірка розроблення DataBench: 100 запитань, по 30 кожного типу, та їхні таблиці
PYTHONUTF8=1 ./venv/Scripts/python.exe -m eval.databench_prep --n 100
# заморожена тестова вибірка: 16 таблиць, які не використовувалися під час розроблення
PYTHONUTF8=1 ./venv/Scripts/python.exe -m eval.databench_prep \
    --split dev --n 150 --out eval/databench_test150.json
```

Розбиття DataBench виконано по таблицях, а не по запитаннях: вибірка
розроблення використовує таблиці 001-049, заморожена тестова вибірка – таблиці
050-065. Тому жодне налаштування, зроблене на вибірці розроблення, не могло
враховувати тестові таблиці.

## 5. Відтворення експериментів

Для прогонів на Gemini спочатку задаються спільні параметри:

```bash
cd "<корінь проєкту>"
set -a && . ./.env && set +a
export PYTHONUTF8=1 VKSK_LANG=en VKSK_LLM_PROVIDER=gemini
export VKSK_LLM_MODEL=gemini-flash-lite-latest
export VKSK_TOKEN_LEDGER=eval/finqa_cache/token_ledger_gemini.jsonl
PY=./venv/Scripts/python.exe
```

### 5.1. Генерація коду проти прямої відповіді (підрозділ 3.7)

| Конфігурація | Команда | Звернень до API |
|---|---|---|
| A: пошук і пряма відповідь (30 рядків), тестова вибірка | `$PY -m eval.databench_run --arm A --tag test150 --dev eval/databench_test150.json --sleep 5` | 150 |
| A на DataBench Lite (вся таблиця з 20 рядків), вибірка розроблення | `$PY -m eval.databench_run --arm A-lite --tag dev100` | 100 |
| B: генерація коду з виправленням помилок, тестова вибірка | `$PY -m eval.databench_run --arm B --tag test150 --dev eval/databench_test150.json` | 152 |
| B на DataBench Lite, вибірка розроблення | `$PY -m eval.databench_run --arm B-lite --tag dev100` | 100 |

Звіт за результатами формується без звернень до API:

```bash
$PY -m eval.databench_compare --tag test150
```

Для конфігурації A параметр `--sleep 5` обов'язковий: промпт містить близько
5 тис. токенів, і без паузи прогін перевищує хвилинний ліміт у 250 тис. токенів
та переривається помилкою 429.

Результати: RESULTS.md, розділи 1-2.

### 5.2. Абляція та аналіз помилок (підрозділ 3.11)

```bash
$PY -m eval.databench_ablation --tag test150   # внесок виправлення помилок і нормалізації
$PY -m eval.databench_errors --arm B --tag test150
```

Абляція повторно виконує збережений у кеші код на локальних таблицях, тому не
потребує звернень до API. Перед обчисленнями перевіряється, що повторне
виконання відтворює результати з кешу.

Результати: RESULTS.md, розділи 4-5.

### 5.3. Пошук таблиці в корпусі (підрозділи 3.10.1-3.10.2)

```bash
$PY -m ingestion.databench_catalog                      # каталог 60 таблиць
$PY -m eval.databench_retrieval --dev eval/databench_test150.json --tag test150
# параметр --run-misses виконує код на знайдених таблицях для запитань, де пошук помилився
```

Пошук виконується методом BM25 за каталогом схем таблиць (назва таблиці, назви
і типи стовпців) без звернень до мовної моделі. Значення клітинок до документа
пошуку не входять, оскільки експеримент показав, що вони погіршують точність
(RESULTS.md, розділ 3.2). Якщо пошук знайшов правильну таблицю, використовується
збережений прогін, тому звернення до API потрібні лише для помилок пошуку.

Результати: RESULTS.md, розділ 3.

### 5.4. Повторний пошук за сигналом виконання коду (підрозділ 3.10.3)

```bash
$PY -m eval.databench_reretrieval --dev eval/databench_dev.json --tag dev100
```

Без параметра `--run` скрипт лише формує план повторних прогонів, з параметром
`--run` виконує їх і витрачає квоту API.

Результати: RESULTS.md, розділ 3.5.

### 5.5. Верифікація згодою маршрутів на FinQA (підрозділ 3.5)

Для цих прогонів використовується Groq:

```bash
export VKSK_LLM_PROVIDER=groq VKSK_LLM_MODEL=openai/gpt-oss-120b
export VKSK_TOKEN_LEDGER=eval/finqa_cache/token_ledger.jsonl
```

```bash
# 1. фіксація вибірки (без звернень до API, записує контрольну суму)
$PY -m eval.finqa_heldout150
# 2. маршрут генерації коду
$PY -m eval.finqa_run --n 2000 --tag heldout150 \
     --only-ids eval/finqa_heldout150.ids --resume
# 3. прямий маршрут, лише після завершення кроку 2 для всіх 150 запитань
$PY -m eval.finqa_baseline --tag heldout150 --mode table \
     --only-ids eval/finqa_heldout150.ids
# 4. аналіз за критеріями успіху, зафіксованими до прогону
$PY -m eval.finqa_confirm --tag heldout150 --expect 150
```

Порядок кроків обов'язковий: скрипт прямого маршруту бере запитання з кешу
маршруту генерації коду, а критерії успіху обчислюються для пар відповідей.
Команди наведено для реплікації на нових запитаннях (підрозділ 3.5.4). Кеші
підтверджувального експерименту (підрозділ 3.5.1) збережено в
`eval/finqa_cache/`.

Результати: RESULTS.md, розділ 7.

### 5.6. Сигнали виконання коду без еталона (підрозділ 3.6)

Усі команди працюють із кешами і не потребують звернень до API:

```bash
$PY -m eval.finqa_scale_rule --tag confirm300   # правило масштабу і знаку
$PY -m eval.finqa_cands --tag confirm300        # кандидати для вибору між маршрутами
$PY -m eval.finqa_repair --tag confirm300 --project   # верхні межі політик вибору
```

Результати: RESULTS.md, розділ 8.

### 5.8. Графіки та промпти

```bash
$PY -m eval.plots            # робочі графіки, eval/figures/
$PY -m eval.plots_thesis     # графіки роботи, eval/figures/thesis/ (300 dpi)
$PY -m eval.shoot_ui         # знімки інтерфейсу (потребує playwright)
$PY -m eval.export_prompts   # тексти промптів для додатка Б, docs/thesis_prompts.md
```

Скрипт `plots_thesis` обчислює кожне число з кешів і звіряє його з очікуваними
значеннями (словник `EXPECTED`); розбіжності виводяться на екран. Серії на
графіках розрізняються кольором і штриховкою, тому графіки читаються і в
чорно-білому друці.

Скрипт `export_prompts` імпортує тексти промптів безпосередньо з модулів, які
надсилають їх моделі. Тому промпти в додатку Б роботи збігаються з тими, що
використовувалися в експериментах.

Для знімків інтерфейсу потрібно встановити playwright:

```bash
$PY -m pip install playwright && $PY -m playwright install chromium
```

## 6. Ліміти безкоштовних тарифів API

| Провайдер | Ліміти | Що обмежує першим |
|---|---|---|
| Groq, `gpt-oss-120b` | 200 000 токенів на добу з поповненням 8 333 на годину; 8 000 токенів на хвилину | хвилинний ліміт на звичайних прогонах, добовий на довгих |
| Gemini Flash-Lite | 500 запитів на добу, 15 запитів на хвилину, 250 000 токенів на хвилину | добовий ліміт на більшості конфігурацій, хвилинний на конфігурації A |

```bash
$PY -m eval.tpd_budget            # залишок добового ліміту токенів Groq
```

Темп прогонів FinQA розраховується автоматично (`eval/finqa_run.auto_pace`) за
хвилинним лімітом.

Рядок у кеш записується лише тоді, коли звернення до моделі відбулося (модуль
`eval/cache_io.py`). Збій з'єднання (помилка 429, тайм-аут, обрив) не
вважається результатом, і запитання лишається для повторного запуску. Помилка
самого методу записується як результат. Перевірити цілісність кешу можна так:

```bash
$PY -c "from eval import cache_io; print(cache_io.audit('eval/finqa_cache/confirm300.jsonl'))"
```

## 8. Обмеження

Повний перелік обмежень наведено в RESULTS.md, розділ 11. Основні з них:

- у всіх конфігураціях на DataBench використано одну модель;
- контекст прямого маршруту обмежено приблизно 12 тис. токенів, оскільки без
  обмеження один промпт містив би 459 тис. токенів;
- еталонні відповіді DataBench хибні приблизно для 8% запитань вибірки
  розроблення (додаток В роботи), а на тестовій вибірці аудит еталонів не
  проводився;
- p-значення в підтверджувальному експерименті не скориговано на множинні
  порівняння.

Перелік виправлених помилок у коді наведено в RESULTS.md, розділ 10.
